## In Progress / Rejected on review

- **The Browse-page stage editor and mobile fix are off the mark — do not resume from this code as-is.** User feedback after looking at it live:
  - The inline `<select>` per catalog row is a UX downgrade: it sizes to its widest option and becomes visually heavy/redundant once tracks accumulate. A native `<select>` is the wrong control for a dense, repeated-per-row edit affordance.
  - Real confusion in testing came from a data/context issue, not just the control: with sparse mock data, everything landed in one big "Unclassified" bucket, which obscured whether song-level grouping and track-level stage were even being tested correctly. "Unclassified" is specifically about song assignment (`CatalogEntry.songId` unset) — a different axis from track stage/status, and the two got tangled visually once both were editable in the same dense row.
  - User re-emphasized: **songs should have their own status concept, separate from track stage.** Tracks may want a sensible non-"unknown" default rather than exposing "unknown" as a real, pickable state.
- The `git checkout -b admin-editing-pass` branch has these changes sitting uncommitted in the working tree — left as-is, not committed, not reverted, so nothing is lost, but also not proposed as the direction going forward.
- A local dev server (`USE_MOCK=true pnpm dev`, port 3001) was left running for the user to inspect; should be safe to kill next session.

But nearly _every single track_ shows "unknown" stage — not a rare edge case. `stageFromPath` (`src/lib/gcs.ts`) is failing to classify almost all real GCS paths, not just the occasional outlier. That's the actual root cause behind "the dropdown is massively redundant as tracks accumulate" — with real data it's a wall of repeated "unknown" boxes, so no per-row editor design fixes this until the classifier itself is fixed.
